# Phase 3.9.9 — Lifecycle Persistence Architecture and Migration Design

Status: design for review. No runtime persistence behavior or user data was
changed for this phase. This document describes the inspected worktree on
2026-10-12; it does not claim production readiness.

`ReviewApproval` is currently an in-memory value passed to `ApplicationEngine.process` and adapter calls. Its validation binds the decision to application ID, normalized job URL, payload fingerprint, and acknowledged question keys. It is not a persisted approval record and must not silently become reusable after restart as part of migration. The engine currently requires a valid approval object for the current call before it creates the durable claim.

Contacts in `contacts.json` are outside the application lifecycle and are not part of this design.

## Design assessment

The current SQLite completion boundary is useful and tested, but it does not make application/attempt lifecycle transitions transactional. A completion transaction commits before JSON projections are repaired. This is recoverable when the SQLite row and matching JSON evidence remain available, but those files are still separate authorities for all earlier states. `ApplicationTracker.create` and ordinary status updates also use JSON read/modify/write without the tracker's process lock, so simultaneous application creation/update is not protected by the completion database's lock.

The next migration should move lifecycle authority into the existing SQLite database in bounded increments. JSON should become a compatibility import/export format, not a second writable authority. Browser operations must always run outside SQLite transactions.

## Proposed minimal relational model

Keep SQLite `PRAGMA user_version` as the schema version. Add tables in a reviewed schema migration; do not rewrite schema version 1 in place.

1. **`applications`** — one row per normalized job identity. Primary key `application_id`; unique `normalized_job_url`; retain original/display URL, company/title, current `ApplicationStatus`, current `AutomationStatus`, contact/notes, applied date, and timestamps. Status values use the existing enum strings. Later business status changes (interview, offer, rejected, withdrawn) update this current row while preserving the immutable completion record.
2. **`attempts`** — immutable identity `(application_id, attempt_number)` with a stable `attempt_id`, FK to application, platform, payload fingerprint, attempt outcome, submission outcome, failure data, retryable flag, and timestamps. Unique `(application_id, attempt_number)`. Do not store resume bytes or full payload merely to persist its fingerprint.
3. **`submission_authorizations`** — one authorization/claim per attempt, FK to attempt, with decision, payload fingerprint, acknowledged-question-key digest/list, and authorization/consumption timestamps. The application call must still present an explicit approval that validates against the current payload. A persisted row is an audit/binding record and one-use claim, not ambient permission to submit after restart. Unique attempt and unique authorization ID.
4. **`browser_observations`** — action ID primary key, FK to authorization/attempt, observer kind, observed URL, application/job/attempt/payload binding, and observed action/result facts. One action per attempt under current semantics; enforce unique attempt unless a future reviewed protocol explicitly supports multiple safe actions.
5. **`verified_evidence`** — evidence ID primary key (canonical digest), unique observation/action FK, attempt FK, exact serialized evidence, and context columns needed for constraints and audit. Evidence must match the same application, normalized URL, attempt, payload fingerprint, and browser action.
6. **`reconciliation_events`** — append-only human reconciliation records tied to application and unknown attempt, recording the supplied human decision, evidence text, and timestamp. This is a distinct provenance from adapter/browser-verified evidence. The existing application does not identify an authenticated human principal; the schema must not pretend the text itself proves identity.
7. **`completion_records`** — at most one completion per application and one per attempt, with a `basis` discriminator and exactly one FK to either verified evidence or a human reconciliation event. A database CHECK enforces the exclusive evidence reference. Browser-verified completions require a `verified_evidence` FK; human-confirmed outcomes require a reconciliation FK. Preserve the application's current business status separately so later interview/rejection transitions do not erase the original completion basis.
8. **`lifecycle_events`** — append-only transition/audit rows with application FK, optional attempt FK, from/to state, event kind, and timestamp. Insert each event in the same transaction as its state update. Migration source/hash and import disposition belong in separate migration metadata/report records, not fake runtime events.

Use `ON DELETE RESTRICT` for lifecycle history. Use CHECK constraints for enum values, positive attempt numbers, nonempty identity/fingerprint fields, and internally valid submission outcome combinations. Use foreign keys for every authorization/action/evidence/completion relationship. Add unique constraints for normalized URL, `(application_id, attempt_number)`, one authorization/action/evidence per attempt under the present protocol, and one completion per application. Use a partial unique index or an equivalent transaction check to prohibit multiple active/uncertain attempts per application.

SQLite constraints cannot establish that a browser observer or human is trustworthy. The application layer must validate explicit approval, evidence provenance, and exact context before writing; database constraints then make validly checked relationships durable and race-safe. Keep trusted browser/evidence recording inside the existing trusted process boundary and document that this does not isolate arbitrary code running in that process.

## Target state and transition rules

Use existing `ApplicationStatus`, `AutomationStatus`, `AttemptOutcome`, and `SubmissionOutcome` strings without inventing aliases. Enforce allowed edges from `VALID_APPLICATION_TRANSITIONS` and `VALID_AUTOMATION_TRANSITIONS` in one persistence service, inside a transaction that reads the current row and appends a lifecycle event. Do not allow callers to update status columns directly.

- `not_started → preparing → needs_review | ready_to_submit | failed | unsupported | human_action_required`.
- `needs_review → preparing | human_action_required`.
- `ready_to_submit → submitting | failed | unsupported | human_action_required`.
- `submitting → submitted | failed | human_action_required | unknown_submission_result`.
- `failed | unsupported | human_action_required → preparing` only under the existing explicit retry/re-entry policy. Keep `unknown_submission_result` non-retryable until a human reconciliation event explicitly resolves it.
- Application business status keeps the existing transition graph. `applied` requires a persisted completion record and its bound evidence basis; do not use a generic status setter to create it.
- Attempt identity is stable: application ID derives from normalized job URL; attempt number is monotonically allocated under a write transaction and unique per application. Payload fingerprint and job identity are immutable for that attempt.
- Browser approval/claim transaction validates current app state, exact explicit approval, required acknowledgements and payload fingerprint; it creates/consumes the one-use authorization and transitions app/attempt to `submitting`. Commit before calling the browser.
- Browser interactions happen with no open SQLite transaction. Persist action observation after the effect. A crash after authorization/action begins is ambiguous; on restart, convert stale `submitting` to `unknown_submission_result` (append event) or leave it explicitly blocked for human reconciliation. Never infer submitted from a stale state and never retry it automatically.
- On adapter verification, validate evidence against the persisted observation and current attempt. In one transaction insert exact evidence, insert completion (FK requires persisted evidence), mark authorization consumed, update attempt to submitted, update application to applied/submitted, and append transition events. This is the atomic success boundary.
- If evidence is absent, mismatched, conflicting, or a browser/security failure occurs, do not insert completion. Persist failure/human-action/unknown state transactionally. Unknown is terminal for automation until explicit human reconciliation.
- Human reconciliation is a separate event and transaction. If the human confirms submission, persist the event and a completion whose basis is `human_reconciliation`; do not forge adapter evidence. If the human confirms it was not submitted, close the unknown attempt with an explicit reconciliation event, then require the existing explicit retry path. Migration itself can never create that human decision.

Each state transition transaction should use `BEGIN IMMEDIATE`, verify expected current state/version, write all related rows and event, and commit. On uniqueness/state conflict, roll back and return a structured conflict; do not overwrite. Browser I/O, profile parsing, resume access, and adapter work stay outside transactions. SQLite locking guarantees are for a local filesystem with working file locks; network/synchronized filesystem use remains unsupported absent separate validation.

## Legacy JSON migration design (not executed)

Provide a future explicit command/API with `--dry-run` as the default and a separate explicit apply/opt-in flag. Do not make normal application startup migrate data. It must use synthetic temporary data in tests and must not be run against real user data as part of this phase.

1. Read sources without modifying them. Capture exact source bytes and SHA-256, parse and validate every row against the current Pydantic models and normalized identity rules, and detect malformed rows, duplicate IDs/URLs, duplicate attempt numbers, inconsistent status pairs, and conflicting SQLite completions.
2. Produce a deterministic report ordered by source path and row index. For each row report `importable_history`, `already_present`, or `quarantined` with stable reason codes and source hash. Do not include credentials, resume content, or unnecessary PII in logs/reports. Two dry runs over unchanged inputs must produce byte-equivalent semantic reports and make no filesystem/database writes.
3. Treat imported state as history only. Do not import active authorization/claim, browser action IDs, browser observations, verified-evidence trust, or retry permission from JSON. In particular, `submitting` and `unknown_submission_result` remain blocked unknown states with retry disabled; never promote them to submitted. Legacy `submitted` is accepted as current submitted only when matched to a valid pre-existing SQLite completion and exact application/attempt/payload/evidence binding. Otherwise quarantine it from authoritative state and preserve the source file unchanged.
4. Preserve safe application and historical attempt data with explicit provenance `legacy_json`, strip authorization/evidence trust, and make imported attempts ineligible for submission replay. Preserve parseable failure/review/human-action records as history, but do not infer that a failure is retryable unless the existing policy plus validated context explicitly permits it. Ambiguous records are quarantined, not silently repaired.
5. Before any opted-in write, make a verified, non-overwriting byte-for-byte backup of every source JSON file and a manifest with path, byte count, hash, timestamp, and target DB schema version. If any backup cannot be verified, abort before DB changes. Never delete or overwrite the source JSON.
6. On apply, acquire the SQLite write lock, record a migration run and each source-row disposition with a stable idempotency key derived from source hash/path/row index, and insert only prevalidated rows. Commit in resumable batches; rerunning skips identical imported rows, while changed/conflicting sources are reported and require review. Store conflicts/quarantine metadata without elevating the corresponding rows to authoritative submission state.
7. Keep migration rollback non-destructive: stop/resume from migration metadata; if operator chooses rollback, remove only rows tagged to that migration after verifying no post-migration lifecycle event depends on them. Prefer leaving imported historical rows and correcting forward over deleting user data.

Schema migration and legacy-data migration are separate operations. Version changes use reviewed SQLite migrations and backup/rollback tests; data import requires explicit opt-in and a completed dry-run review. No production migration is part of Phase 3.9.9 design validation.

- Legacy JSON is not trusted as a completion: `tests/test_submission_persistence.py::test_legacy_json_is_not_imported_as_trusted_completion`.

Phase 3.9.10 adds a read-only planner that emits a deterministic report for JSON application/attempt snapshots and an optional existing schema-version-1 or schema-version-2 SQLite completion database. It does not import records or provide backups or migration resume behavior.

Phase 3.9.12 implements SQLite schema version 2 on synthetic/local test databases. It adds separate lifecycle application/attempt history, migration run/unit and quarantine metadata, and lifecycle transition events while preserving the existing `submission_completions` table as the trusted-success boundary. Schema initialization upgrades a validated version-1 database transactionally and rejects unsupported or malformed schema metadata. No legacy JSON migration executor or production data migration is implemented. Imported historical records have no authorization, browser observation, or verified-evidence columns; unknown attempts are constrained to non-retryable. Lifecycle tables are not yet wired as the runtime source of truth.

The v2 ownership and transaction contract is:

- `lifecycle_applications` stores historical/runtime lifecycle state with unique application and normalized-URL identities. Applied/submitted states require a matching existing trusted completion. Database triggers enforce the existing business and automation transition graphs and append `lifecycle_events` in the same SQLite statement transaction. Imported initial snapshots do not create synthetic transition events.
- `lifecycle_attempts` stores attempt identity, normalized job identity, payload fingerprint, outcome, retryability, and provenance. `(application_id, attempt_number)` and `attempt_id` are unique; identity/provenance fields are immutable. Unknown outcomes require `submission_outcome=unknown` and `retryable=0`; imported attempts are always non-retryable. Submitted attempts require an exact matching v1/v2 trusted completion. The table has no approval, authorization, browser-action, observation, or evidence columns.
- `migration_runs` binds a stable run ID to the reviewed plan digest and source manifest. `migration_units` stores one stable source-row disposition under a run and a unique source identity. Imported units carry a deferred FK to exactly one target application or attempt; the target record points back to the unit. Those deferred reciprocal FKs require the unit and imported historical record to commit in the same transaction. Units are append-only. A running migration can finish or fail; units cannot be added after the run is terminal.
- `migration_quarantines` stores sanitized details for quarantined units only. Inserting a quarantined unit creates its quarantine row in the same transaction; the unit's reason code is required. A quarantined/excluded unit cannot point to an authoritative lifecycle record.
- `submission_completions` remains the separate trusted adapter-evidence completion table. The v1-to-v2 upgrade neither rebuilds nor rewrites its rows. Schema initialization uses `BEGIN IMMEDIATE`, validates the prior schema and every existing completion, adds v2 objects, sets `PRAGMA user_version=2`, validates the resulting schema/integrity/foreign keys, and commits. Any failure rolls back the schema changes. This relies on SQLite transaction and local file-lock behavior; it makes no additional hardware or network-filesystem durability claim.

SQLite enforces relational identities and statuses, but it cannot independently prove a legacy source's identity or the truth of a reviewer's migration plan. Those checks remain the responsibility of a future explicit executor. Schema v2 does not itself authorize or perform imports.

## Validation boundary and open limitations

Phase 3.9.9 was a design review and made no source/runtime behavior changes; its original uncommitted Phase 3.9.6-3.9.8 changes remain preserved. Phase 3.9.12 adds schema support only: current application runtime still uses JSON for lifecycle state and SQLite for trusted completion, and the new lifecycle tables are not yet an application source of truth. Local fixture verification does not establish production ELEKS confirmation behavior. Process locks and SQLite guarantees have only been exercised on the local Windows test environment; no network/synchronized filesystem guarantee is made.
